# Практикум №7 — Профілювання та оптимізація

Той самий домен (`products`), що й у практикумах №4–6. Ендпоінт для вимірювання:
`GET /api.php?resource=products`.

- `?mode=naive` — свідомо "повільна" версія: N+1-запит для суми `price*stock`.
- без `mode` (або `mode=optimized`) — один агрегатний запит `SUM(price*stock)` + файловий кеш (TTL 60с).

Запущено на: `php -S localhost:8000`, база `practicum4` (MySQL/MariaDB). У каталозі на момент замірів **10 товарів** (N = 10).

---

## Крок 1–2. Базова лінія "до" (режим `naive`)

### Профілювання (з поля `meta` у відповіді)

```bash
curl -s "http://localhost:8000/api.php?resource=products&mode=naive" | python3 -m json.tool
```

```json
"meta": {
    "mode": "naive",
    "query_count": 11,
    "elapsed_ms": 4.2,
    "memory_mb": 2,
    "cache": "n/a"
}
```

| Показник | Значення |
|---|---|
| Час виконання (мс) | 4.2 (перший, "холодний" запит; повторний запит — 1.05) |
| Пікова пам'ять (МБ) | 2 |
| Кількість SQL-запитів | 11 (1 + N, N = 10 товарів) |

### Навантажувальне тестування

```bash
ab -n 200 -c 20 "http://localhost:8000/api.php?resource=products&mode=naive"
```

| Показник | Значення |
|---|---|
| Requests per second | 1528.99 |
| Time per request (mean), мс | 13.081 |
| Failed requests | 17 (усі — типу `Length`, див. примітку нижче) |

> **Примітка щодо `Failed requests`.** Усі збої мають тип `Length` (`Connect: 0, Receive: 0, Exceptions: 0`).
> `ab` вважає запит невдалим, якщо довжина тіла відрізняється від першої відповіді. Тут відповідь
> містить змінні поля `meta.elapsed_ms` / `meta.cache`, тому її довжина коливається на кілька байтів.
> Це не реальні помилки: усі 200 запитів отримали коректну відповідь. Щоб отримати 0, можна запустити
> `ab` з ключем `-l` (не перевіряти довжину відповіді).

## Крок 3. Підтвердження проблеми N+1

`meta.query_count` у режимі `naive` дорівнює **11 = 1 + N** (N = 10 товарів у каталозі):
1 запит на список `SELECT * FROM products` і ще по одному запиту `SELECT price*stock ... WHERE id=:id`
на кожен товар у циклі. Це і є проблема N+1: кількість запитів росте лінійно з розміром каталогу.

## Крок 4. Індекс на стовпці `sku`

Фільтр `findBySku()` використовує `WHERE sku = :sku`. Перевірка через `EXPLAIN`:

```sql
EXPLAIN SELECT * FROM products WHERE sku = 'MAT-003';
```

Результат (MySQL 8, деревоподібний формат виводу):

```
-> Rows fetched before execution  (cost=0..0 rows=1)
```

Це означає, що оптимізатор розпізнав пошук за унікальним ключем (тип доступу `const`) і прочитав
єдиний рядок ще на етапі оптимізації, без сканування таблиці (`type=ALL` немає, `rows=1`).

**Важливо:** стовпець `sku` у схемі (`schema.sql`, практикум №4) оголошений як `UNIQUE`,
а `UNIQUE` в MySQL автоматично створює індекс. Тому фільтр за SKU був оптимізований ще з практикуму №4,
**до** явного `CREATE INDEX`. Для унікального індексу з пошуком за рівністю очікуваний тип — саме `const`
(а не `ref`, який характерний для неунікальних індексів).

Явний індекс (для відповідності кроку методички) усе одно доданий у `schema.sql`:
```sql
CREATE INDEX idx_products_sku ON products (sku);
```
Він технічно надлишковий (дублює індекс від `UNIQUE`): не змінює план запиту, але трохи
сповільнює `INSERT`/`UPDATE`. У реальному проєкті його варто прибрати.

| | Тип доступу | rows |
|---|---|---|
| До (з UNIQUE, без явного CREATE INDEX) | const (індекс `sku`) | 1 |
| Після (з явним CREATE INDEX) | const (той самий план) | 1 |

## Крок 5. Усунення N+1

```bash
curl -s "http://localhost:8000/api.php?resource=products" | python3 -m json.tool
```

Фактична відповідь (перший запит, кеш порожній):

```json
"meta": {
    "mode": "optimized",
    "query_count": 2,
    "elapsed_ms": 2.02,
    "memory_mb": 2,
    "cache": "miss"
}
```

`meta.query_count` тепер дорівнює **2** при першому запиті (1 — список товарів,
1 — агрегатний `SELECT SUM(price*stock)`), замість 11. Замінено цикл з окремим
запитом на кожен товар (`getTotalStockValueNaive()`) одним агрегатним запитом
(`totalStockValue()`), що виконує підсумовування безпосередньо на стороні СУБД.

Результат збігається з наївним режимом: `total_stock_value = 121650.48`.

## Крок 6. Кешування

Повтори той самий запит ще раз протягом 60 секунд:

```bash
curl -s "http://localhost:8000/api.php?resource=products" | python3 -m json.tool
```

Другий (і кожен наступний у межах TTL) виклик має показати `"meta.cache": "hit"`
і `meta.query_count = 1` (лише список товарів — сам агрегат узятий з файлового
кешу без повторного запиту до БД). Через 60 секунд кеш протухає природно
(`cache: "miss"` знову, і файл кешу перезаписується).

Кеш лежить у `sys_get_temp_dir()` з назвою `practicum07_cache_<hash>.json`.
Якщо дані зміняться (наприклад, при `INSERT`/`UPDATE` з практикуму №4 чи №6),
правильна практика — викликати `invalidateCache('total_stock_value')`
(є в `lib/cache.php`) одразу після запису, щоб кеш не показував застарілу суму
до завершення TTL.

## Крок 7. Повторний замір "після" (режим `optimized`)

```bash
curl -s "http://localhost:8000/api.php?resource=products" | python3 -m json.tool
ab -n 200 -c 20 "http://localhost:8000/api.php?resource=products"
```

| Показник | До (naive) | Після (optimized) |
|---|---|---|
| Час виконання (мс) | 4.2 (повторно 1.05) | 2.02 (cache miss, 2 запити) |
| Пікова пам'ять (МБ) | 2 | 2 |
| Кількість SQL-запитів | 11 (1 + N) | 2 при miss / 1 при cache hit |
| Requests per second (ab) | 1528.99 | 3075.27 |
| Time per request, mean (ab), мс | 13.081 | 6.503 |
| Failed requests (ab) | 17 (Length) | 199 (Length) |

> **Примітка щодо `Failed requests` у режимі optimized.** Як і в `naive`, усі збої — лише `Length`
> (`Connect: 0, Receive: 0, Exceptions: 0`). Перша відповідь була `cache: "miss"`, решта — `cache: "hit"`
> зі змінною довжиною `meta`, тож `ab` порівнює їх з першою за довжиною. Реальних помилок немає;
> з ключем `-l` значення буде 0.

Висновки за `ab` (200 запитів, 20 одночасних):

- пропускна здатність зросла з 1529 до 3075 req/s — приблизно **у 2 рази**;
- середній час запиту впав з 13.08 до 6.50 мс — приблизно **на 50 %**;
- 95-й перцентиль впав з 22 до 10 мс, максимум — з 25 до 12 мс.

Пам'ять не змінилась (2 МБ) — це мінімальна одиниця округлення `memory_get_peak_usage(true)`
для такого малого набору даних; оптимізація тут стосується запитів і часу, а не пам'яті.

---

## Крок 8. Висновок

Час виконання й кількість SQL-запитів падають (11 → 2 при miss і → 1 при cache hit; пропускна здатність
зросла з ≈1529 до ≈3075 req/s), бо замість N окремих запитів по одному товару виконується єдиний
агрегатний запит `SUM(price*stock)` на стороні MySQL, а повторні запити протягом TTL взагалі не звертаються
до БД завдяки файловому кешу; при зростанні каталогу вигода тільки збільшуватиметься, бо naive-режим
масштабується лінійно (1 + N).
